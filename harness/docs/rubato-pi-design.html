rubato-pi — 기반 선택과 OMO component 결정

rubato-pi는 기존 rubato(fx 포크 + fx-v3-bridge)와 별개로 Senpi 엔진 계열 위에 올리는 두 번째 실행 하네스 후보다. 이 화면의 할 일은 하나다 — OMO Native가 얹어 주는 18개 component를 각각 유지할지, 기본 OFF로 둘지, 보류할지 정하고, OMO의 task만 재사용하는 후보 C(thin overlay)가 채택 조건 6개를 통과하는지 판정하는 것.

작성 2026-08-22 · 근거 문장의 정본은 rubato-pi-design.md이며, 이 화면과 충돌하면 정본이 우선한다.

  1. 기능 이해 — 한 줄 요약을 보고, 영향·의존성이 필요하면 상세 보기를 연다.
  2. 결정 기록 — v0 제안은 자동 선택되지 않는 참고안이다. 유지·기본 OFF·보류는 언제든 바꾸거나 초기화할 수 있다.
  3. 채택 판정 — 18개 결정을 마치면 후보 C의 채택 조건 6개와 공식 소스 근거를 검토한다.

01문서의 현재 상태

무엇이 정해졌고 무엇이 안 정해졌는지를 먼저 갈라 둔다. 추천이 나중에 뒤집힐 때 무엇이 무너진 것인지 추적하기 위해서다.

결정 완료

  • rubato-pi는 OMO Native 기반을 우선 검토 대상으로 삼는다. 백지에서 Senpi 위에 직접 짓는 안은 폐기가 아니라 비교 대상으로 남는다.
  • OMO의 개별 기능(ultrawork 계열, memory 계열 등)은 꺼도 된다. 다만 끄기 전에 전체 목록을 파악한 뒤 선택한다 — 그 목록이 아래 결정표다.

미결정

  • 세 후보(bare Senpi custom / OMO monorepo fork / OMO task-only thin overlay) 중 무엇을 채택할지. thin overlay는 확정된 추천이 아니라 현재 증거상 가장 싼 v0 실험 후보이며, gate 1~6을 모두 통과해야 채택 가능해진다.
  • 18개 component 각각의 유지 · 기본 OFF · 보류.
  • 버전 pin 정책의 구체적 형태(정확 pin의 갱신 주기, 누가 allowlist를 갱신하는지).
  • rubato-pi가 기존 rubato(fx)를 대체하는지, 병행하는지, 특정 역할만 가져가는지.
  • 외부 배포 여부. 이것이 정해져야 라이선스 제약이 실제 제약이 되는지 결정된다.

검증한 것과 검증하지 않은 것

여기 적힌 구조·동작 주장은 (a) 로컬 설치물 /opt/homebrew/lib/node_modules/omo-ai의 실제 파일, (b) upstream dev 브랜치의 고정 commit 소스, (c) Senpi 공식 문서, (d) 로컬 beta.7을 RPC 모드로 띄워 get_commands로 명령·스킬 표면을 읽은 실측 중 하나에 대응한다.

실행 실측은 (d) 범위에서만 했다

확장 적재 형태별 명령·스킬 표면과 disable 플래그의 CLI 반응은 프로세스를 띄워 쟀다. 반면 캐시 적중률, 컴팩션 연속성, crash/resume, 팀원 자식의 확장 상속은 재지 않았다 — 검증 지표에 "측정해야 할 것"으로만 있다. 실측 대상은 로컬 beta.7이므로 upstream dev에 그대로 옮겨 말할 수 없다.

02OMO Native의 계층

omo 명령 하나가 소유자가 서로 다른 세 계층을 세운다. 이 분해가 이후 모든 선택의 전제다.

  1. launcher omo-ai 패키지 · bin/omo.js → bin/lib/launcher.js
    • Senpi 엔진 경로를 해석해 spawn 한다.
    • SENPI_BRAND로 이름 · 설정 디렉토리 · env prefix · update 채널을 주입 (name omo, configDir .omo, envPrefix OMO, distTag beta).
    • SENPI_CODING_AGENT_DIR = ~/.omo/agent, OMO_NATIVE=1(footer 배지 마커).
    • --extension <plugin 경로>를 앞에 붙여 확장을 적재한다.
  2. spawn (Node)
  3. OMO extension Pi 패키지 @code-yeongyu/omo-senpi
    • plugin/extensions/omo.js — 단일 번들 진입점.
    • plugin/skills/ — 실측 22개 적재. plugin/runtime/ — ast-grep MCP, LSP daemon, agent-toolkit.
    • component를 등록 순서대로 register (dev 18개 / 로컬 beta.7 16개).
    • 전역 플래그 omo-senpi-disabled + component마다 omo-senpi-<name>-disabled.
  4. Senpi ExtensionAPI
  5. Senpi engine @code-yeongyu/senpi (MIT)
    • 모델 라우팅 / 프로바이더 OAuth / 프롬프트 캐시 / 컴팩션 / 권한 / 도구(PTY bash 계열) / 스킬 로더 / 세션 저장·분기 / MCP 클라이언트 / TUI.

세 번째 계층이 만드는 결합

launcher가 하는 일은 "브랜드 주입"이라고 부르기에는 범위가 넓다 — 설정 디렉토리(~/.omo/agent), 환경변수 prefix, 업데이트 채널(omo-ai@beta), wire 상의 user-agent까지 바꾼다. rubato-pi가 OMO 확장만 재사용하고 브랜드를 자기 것으로 가져가려면 이 launcher를 쓰지 않고 직접 대체해야 한다. 우회가 아니라 계층이 원래 그렇게 갈라져 있다는 뜻이다 — 확장은 Senpi의 표준 Pi 패키지 규약을 따르므로 launcher 없이도 적재된다.

로컬 설치물과 upstream을 혼동하지 않는다

로컬은 omo-ai@5.0.0-0.beta.7(엔진 2026.8.12-4), upstream dev(commit 024cd9f)는 beta.15(엔진 2026.8.21-3)다. 확인된 차이 셋.

  • component 개수 — 로컬 16개, upstream 18개. beta.7 번들에는 git-master와 mass-ulw가 component로 등록되지 않는다. 이 화면에서 "18"은 언제나 dev를 가리킨다.
  • dag와 팀원 프로세스 분기는 beta.7에 없다. 로컬 번들에 dag 도구와 isTeamMemberProcess 식별자가 둘 다 0회다. 도구 개수(11개), 승인 gate 대상, 중첩 위임 판정은 전부 upstream dev 기준이다.
  • component별 disable 플래그도 beta.7에는 없다. dev의 compose.ts는 18개 전부에 omo-senpi-<name>-disabled를 registerFlag 하지만, beta.7 번들의 플래그 이름은 7개뿐이다. 로컬에서 --omo-senpi-memory-disabled, --omo-senpi-disabled, =true 변형까지 붙여 봤지만 어느 것도 component를 끄지 못했다. 이것이 gate 5의 출처다.

엔진 pin은 OMO의 설계 의도이기도 하다 — launcher가 omo update self류를 가로채고 "엔진이 이 패키지에 pin 되어 있으므로 self-update는 pairing을 깬다"고 답한다.

03세 후보 비교

셋 다 Senpi를 엔진으로 쓴다. 갈리는 것은 OMO 코드에 대한 소유권을 얼마나 가져오는가이다.

후보 A — bare Senpi custom

Senpi를 그대로 쓰고 Taskforce에 필요한 것(팀 통신, 역할 계약, 완료 증거)을 우리 확장으로 새로 쓴다. OMO는 참조만 한다. 얻는 것은 표면적의 최소화 — upstream 추적이 Senpi 하나로 끝나고 라이선스도 MIT 단일이다. 잃는 것은 OMO의 task/team 엔진 전부다: persistent child, 직접 peer messaging, 내구 mailbox, exactly-once 배달 원장, crash/reload/resume 재조정, 컴팩션 중 버퍼링, DAG/status. fx Team Overlay에서 의도적으로 만들지 않았던 것들(broadcast, 공유 task 원장, 중첩 팀)이 여기서는 OMO가 이미 갖고 있는 것들이다.

후보 B — OMO monorepo 삭제식 fork

포크하고 필요 없는 것을 지운다. 얻는 것은 완전한 개조 자유 — component 경계를 다시 긋고 senpi-task 내부 의미(완료 증거 필드 추가 등)를 직접 고칠 수 있다. 잃는 것 둘: upstream 추적이 이 레포가 이미 아는 조용한 실패를 부르고(fx 포크의 control_store.zig 스키마 충돌, OMO는 packages 46개로 표면적이 더 넓다), 루트가 Sustainable Use License라 포크물의 외부·상업 배포가 막힌다.

후보 C — upstream OMO task-only thin overlay (v0 실험 후보, 조건부)

Senpi와 OMO 확장을 정확 버전 pin으로 설치만 하고 포크하지 않는다. 필요한 component만 켜고 나머지는 disable 플래그로 끄며, Taskforce 의미론은 우리 쪽 얇은 어댑터 확장이 얹는다. 근거는 하나다 — 개조 비용 사다리에서 가장 싼 쪽부터 시도한다. 가장 싼 형태는 이번 실측으로 좁혀졌다: plugin/extensions/omo.js 파일 하나를 -e로 지정하면 component와 task 엔진은 그대로 들어오면서 OMO 스킬 22개는 따라오지 않는다. 포크도, 패키지 필터 설정도 필요 없다.

그러나 같은 조사에서 gap 넷이 소스로 확인됐다

팀원의 중첩 위임 불가, 역할 계약의 시스템 프롬프트 주입 경로 부재, 자식별 permission 전달 필드 부재, 팀원의 task board 직접 접근 부재. 이 중 permission은 pretrusted 역할별 전용 worktree 설정으로 해결될 가능성이 남아 있고, 나머지는 현재 설정으로 열리지 않는다. 여기에 아직 재지 않은 것 둘이 붙는다 — 팀원 자식의 확장·disable 상태 상속(gate 4), disable 플래그를 실제로 세울 수 있는지(gate 5).

깨지는 자리에 따라 갈 곳이 다르다

  • gate 1~2가 해결되지 않으면 → 후보 B로 승격. 둘은 OMO task internals의 개조를 요구한다. gate 3은 pretrusted 전용 worktree E2E가 실패하거나 worktree 공유가 필수일 때만 같은 승격 후보가 된다. 포크 범위는 senpi-task + omo-senpi/components/task로 좁힐 수 있다.
  • gate 4(자식 상속)가 깨지면 → 후보 A가 살아난다. 확장을 자식까지 전달할 방법이 없다는 뜻이므로 task/team 재구현 비용과 재비교한다.
  • gate 5(플래그)가 깨지면 → 대안 경로를 먼저 찾고, 없으면 후보 B. component를 못 끄면 "필요한 것만 켠다"는 후보 C의 정의가 성립하지 않는다.

승격 기준 — 실험을 접는 조건을 미리 못 박는다

  1. gate 1~2와, 전용 worktree PoC가 실패한 gate 3의 해법이 모두 "자식에 강제 적재되는 우리 확장이 OMO 내부 동작을 되돌려 놓는" 형태로 수렴할 때. 그 어댑터는 이미 thin overlay가 아니라 바깥에서 하는 포크다.
  2. 하나의 gate를 통과시키려 넣은 우회가 다른 gate를 깨서 되돌리는 일이 반복될 때. 내부 패치가 얽히면 pin을 올릴 때마다 전부 재검증해야 하고, 이것이 fx 포크의 조용한 실패와 같은 모양이다.

04component 18개 결정

목록과 등록 순서의 정본은 packages/omo-senpi/src/extension/component-list.ts (commit 024cd9f)다. 순서에는 의미가 있다 — 예를 들어 start-work-continuation이 ulw-loop보다 먼저 등록되어야 boulder 작업이 우선권을 갖는다. compose.ts가 각 component에 omo-senpi-<name>-disabled 플래그를 등록하고 true면 건너뛴다. 소스상으로는 18개 전부가 개별적으로 꺼진다.

"소스에 플래그가 있다"와 "우리가 그 플래그를 세울 수 있다"는 다른 문제다

로컬 beta.7에서 이 플래그들을 CLI 인자로 넘겨 봤더니 전역·개별 어느 쪽도 효과가 없었다. beta.7은 플래그가 7개뿐이라 dev의 결과를 대신하지 못하지만, 짚이는 구조는 dev에도 그대로 있다 — compose.ts는 확장이 활성화되는 시점에 registerFlag를 하고 곧바로 같은 함수에서 getFlag로 읽는데, 그 시점은 CLI가 argv를 파싱한 뒤다. "플래그로 끈다"는 후보 C의 전제이면서 동시에 검증되지 않은 전제이고, gate 5로 다룬다.

선택 기준

  • 유지 — 그 기능이 없으면 rubato-pi가 목적을 못 이룰 때만.
  • 기본 OFF — 기능은 이해했고 필요 없다고 판단했을 때. 나중에 플래그 하나로 되돌린다.
  • 보류 — 근거가 부족할 때. v0에서는 꺼진 상태로 출발하되, 어떤 지표를 재야 결정되는지를 함께 적는다.

"v0 제안"은 추천이지 결정이 아니다. 초기 상태는 18개 전부 미결정이며, 추천값이 자동으로 선택되지 않는다. 결정 컨트롤은 이 표 한 곳뿐이고, 아래 상세 카드는 읽기 전용이다.

05Senpi builtin — 다시 만들지 않을 것

fx 포크에서 직접 깎았던 것 상당수를 Senpi가 이미 갖고 있다. 여기 적힌 것은 재구현 금지 목록이다 — 우리 코드로 옮기는 순간 두 번째 정본이 생긴다.

프롬프트 캐시

  • Claude SDK OAuth(구독) 레인은 SDK가 cache_control을 소유하므로 Senpi가 breakpoint를 못 넣는다. 그래도 300초로 보고해 캐시 인지 예산이 제 크기를 잡게 한다. 재정의 불가.
  • 직접 Anthropic API 레인은 기본 5분이고 cacheRetention: "long" 또는 PI_CACHE_RETENTION=long으로 1시간을 켠다. 1시간 쓰기가 base input의 2배라는 비용 구조까지 문서가 명시한다 — 기존 rubato가 독립적으로 실측해 도달한 결론과 같다.
  • Anthropic 호환 프로바이더(kimi-coding, fireworks, gateway류)는 1시간 TTL이 native base URL에 gate 되어 있어 short로 남는다.
  • 재정의 우선순위: models.json/카탈로그의 cacheRetention > PI_CACHE_RETENTION > 레인 기본값.
  • 서버 affinity도 builtin이다. Anthropic 구독 레인은 rendezvous 해싱으로 한 세션이 한 계정에 붙는다. OpenRouter는 세션 id를 x-session-id 헤더와 body 양쪽으로 보내고, Moonshot에는 prompt_cache_key, Cloudflare에는 x-session-affinity가 자동으로 붙는다.
  • 캐시 인지 타임아웃은 fx에서 만들지 않은 종류다. promptCache.cacheAwareTimeouts(기본 true)가 foreground 도구 대기를 캐시 TTL에서 safetyBufferSeconds(기본 30)를 뺀 값으로 상한 건다. 예산에 걸린 명령은 죽이는 대신 살아 있는 background 세션으로 넘긴다.
  • parked 세션의 wake source 집계 — wake_source_state를 terminal monitor, background bash, detached eval, senpi-task(OMO의 background 자식과 소유 팀원)가 발행하고, 하나라도 근무 중이면 캐시 TTL 안에서 대기한다.

컨텍스트와 컴팩션

  • 자동 트리거는 contextTokens > contextWindow - reserveTokens (compaction.reserveTokens 기본 16384). 컷 포인트는 뒤에서부터 keepRecentTokens(기본 20000)까지 모은다.
  • 사유는 manual / threshold / overflow 셋. overflow는 컨텍스트 초과로 턴이 중단된 뒤의 복구 경로이며 willRetry로 재시도 여부를 알린다.
  • 컴팩션·branch 요약 요청은 새 라우팅 세션 id를 쓰고 프로바이더가 지원하면 캐시 쓰기를 끈다 — 재사용 가능성이 없는 일회성 프롬프트이기 때문이다.
  • 확장이 session_before_compact / session_compact_failed / session_before_tree로 요약을 가로챌 수 있다.
  • 요약 실패는 무한 재시도가 아니라 유한 예산이며, "speculative warm-up"은 자기 idle 재시도를 따로 갖는다.

컨텍스트·규칙 중복 제거

  • 컨텍스트 파일은 AGENTS.md 또는 CLAUDE.md를 계층적으로 적재하고, AGENTS.override.md가 있으면 그 디렉토리에서 그것을 대신 쓴다. --no-context-files로 끈다.
  • 동적 project rule은 대상이 달라도 본문이 다시 붙지 않는다 — 규칙 본문은 하나의 live-context 중복 제거 범위를 공유하며, 컴팩션이 경계를 지우거나 내용 해시가 바뀔 때까지 재주입되지 않는다.
  • 스킬은 심링크 별칭을 canonical path로 중복 제거한다. 이 레포의 정본 배치(~/.agents/skills/에 실체, 각 CLI가 심링크)가 그대로 통한다.

권한 — 그리고 그 한계

프리셋(full-access, workspace, read-only, ask)을 먼저 평가하고 전역 설정 → 프로젝트 설정 → CLI 플래그 순으로 명시 규칙을 적용한다. 마지막에 맞는 규칙이 이긴다. read-only는 read/list/grep을 허용하고 edit/bash/external_directory를 묻는다.

권한 규칙은 확인 정책이지 샌드박스가 아니다

문서가 명시한다 — Senpi, 확장, 패키지 설치, 자식 프로세스는 여전히 호스트 프로세스 권한으로 돈다. gate 3의 verifier 쓰기 차단은 이 한계 위에 설계해야 한다.

background terminal · 모델 fallback · 캐시 연속성 관측

  • bash는 실제 PTY 위에 있고 동반 도구 다섯이 딸린다: bash_output(비차단 peek, regex 필터), monitor(장기 명령 감시), bash_input, bash_resize, kill_bash(트리 kill). background 세션은 timeout으로 죽지 않고 /reload를 넘어 살아남는다.
  • 모델 fallback은 전환이 현재 턴을 이어가며 기존 대화 접두를 바꾸지 않는다 — 캐시 입력이 보존되고 수명주기 이벤트는 모델 컨텍스트에 들어가지 않는다. 쿨다운은 오류에서 유도되며 프로바이더의 retry-after 힌트가 항상 이긴다.
  • 세션 로그의 kind가 bootstrap/delta/reattach/fork/flatten/disabled 중 하나다. flatten이 반복되면 그 레인이 대화 전체를 재전송해 캐시 적중을 잃고 있다는 뜻이다. SENPI_SESSION_DEBUG=1이 같은 라인을 stderr로 미러한다.

06task/team과 Agent Taskforce의 간극

재사용할 수 있는 것

  • persistent child와 두 실행 모드. in-process 러너는 부모의 살아 있는 도구 클로저를 공유하고(task_*/team_* 계열은 제외), process 러너는 자식 Senpi 프로세스를 띄워 JSON-RPC로 steer/abort/prompt를 건넨다. 일반 task/dag child와 team_create 멤버가 같은 process-child 운반체를 쓰지만 의미는 다르다 — 멤버만 team identity, member extension, mailbox, team runtime state를 받는 resident peer다. caller-worker subagent가 아니며, team_create도 작업 결과를 기다리지 않고 spawn 완료만 반환한다.
  • 직접 peer messaging. fx Team Overlay에서 Zig 소스를 고쳐가며 얻었던 바로 그 능력이 OMO에는 이미 있다.
  • 내구 mailbox와 exactly-once 원장. unread <messageId>.json → .delivering-<messageId>.json → 수신 세션에서 메시지가 관측된 뒤에만 processed/<messageId>.json으로 커밋. processed 파일이 내구 원장이다.
  • crash/reload/resume 재조정. 모든 session_start가 정해진 순서의 복구 체인을 돈다: 버퍼된 완료 flush 또는 drop → reconcile(정지된 자식 부활, 내구 process 멤버 재부착) → 소유 멤버 liveness 재관측 → 오래된 예약 회수 → 미통지 완료 재배달 → await TTL 정리 → 소유 리드 poll → 상태 동기화.
  • 컴팩션 중 버퍼링. 완료 라우팅이 부모 상태에 따라 갈린다: idle → wake, streaming → 즉시 전달, compacting/session_switching/session_shutdown → 부모가 안정될 때까지 buffer.
  • DAG/status 저장소. Task 스키마에 status(pending/claimed/in_progress/completed/deleted), owner, blocks, blockedBy가 있다. 다만 peer-shared board는 아니다 — board 도구는 리드에만 등록되고 팀원 확장은 task_send 하나만 제공한다.

"launcher만 바꾸면 Taskforce 요구가 전부 OMO에 있다"는 정리는 채택하지 않는다

위 목록이 재사용 가능한 것의 전부이고, 그것은 배관이다 — persistent child, mailbox, board, 복구 체인. Taskforce가 요구하는 의미론은 그 위에 있고, 현재 OMO에는 팀원의 중첩 위임, 역할 계약의 무조건 주입, verifier 권한 정책의 직접 전달, 팀원의 board 직접 접근이 없다. 앞의 둘과 board 접근은 소스에 경로가 없고, verifier 권한은 spawn spec/argv의 직접 전달 경로가 없지만 pretrusted project settings 우회는 아직 실측 전이다. 배관이 훌륭하다는 사실과 그 위에 우리 의미론을 얹을 자리가 있다는 사실은 다른 주장이다.

의미가 어긋나는 것

사용자 roster 승인 gate가 없다

TeamSpecSchema에 사용자 승인 필드가 없다. 팀 생성은 team_create 호출 한 번이고 모델이 그것을 부를 수 있다. Taskforce는 "리드가 최소 모델·역할 배치안을 먼저 사용자에게 보고하고 승인 뒤 teammate를 띄운다"를 스킬의 정의로 갖는다. gate를 걸어야 할 대상은 실제로 자식을 띄우는 세 도구다 — team_create(spawnTeamMembers), task(manager.start), dag(노드마다 자식). task_create는 대상이 아니다 — 이름이 비슷하지만 tasklist 레코드 생성이고 프로세스를 만들지 않는다.

board는 멤버가 claim하도록 설계됐는데, 멤버가 부를 도구가 없다

아래층인 team-core team-tasklist는 멤버 이름 단위 claim을 제대로 구현한다 — claimTask(teamRunId, taskId, memberName, config)가 파일 락으로 경합을 막고, 이미 claim된 것은 AlreadyClaimedError, blockedBy가 안 풀린 것은 BlockedByError로 거절하며, updateTaskStatus는 task.owner !== memberName이면 CrossOwnerUpdateError를 던진다. 즉 여러 peer가 하나의 board를 두고 경쟁하는 상황을 전제한 기제다. 위층은 그 전제를 따라가지 않는다 — board 도구 4개는 buildLeadTeamTools로 리드에만 등록되고, 서비스 메서드는 전부 assertOwnedTeam으로 소유 리드 세션인지 먼저 검사한다.

그 결과가 갈린다. 리드의 task_update는 owner 파라미터를 받고 기본값만 리드이므로, 리드 중개 board는 추가 코드 없이 오늘 성립한다. 그러나 이는 팀원이 직접 접근·claim·update하는 Taskforce의 shared board 요구를 충족하지 않는 축소안이다. 멤버가 스스로 board를 읽고 자기 이름으로 claim하는 경로는 도구가 없어 막히며, gate 6에서 열어야 한다.

역할 계약을 시스템 프롬프트로 주입할 경로가 없다

buildMemberPrompt가 member.prompt를 다른 안내 문장 넷과 이어붙여 하나의 문자열로 만들고, 그것이 자식의 첫 프롬프트가 된다. 시스템 프롬프트 채널이 아니다. 계약 파일 경로를 가리키는 포인터도 보장 수단이 아니다 — 모델이 그 파일을 읽을지는 모델에 달렸고, 컴팩션 뒤 첫 프롬프트가 요약에 흡수되면 계약은 사라진다. 즉 현재 OMO에서 역할 계약은 "지켜지길 기대하는 텍스트"이지 "무조건 실리는 계약"이 아니다.

process 멤버는 중첩 위임을 할 수 없다

제약이 아니라 부재다. createTaskComponent의 register가 첫 줄에서 if (isTeamMemberProcess()) return으로 빠져나간다 — 팀원 프로세스에서는 task component 자체가 등록되지 않고 도구 11개가 전부 없다. 그 자리의 멤버 확장은 task_send 하나만 등록한다. fx에서는 팀원이 headless로도 자기 자식을 띄우고 inspect.wait로 거둘 수 있음을 2026-08-21에 실측했지만, OMO에서는 같은 것이 설정으로 열리지 않는다.

persona tool policy가 멤버에서 강제되지 않는다

curated read-only 에이전트 4개는 in-process에 고정되어 있고, member-validator.ts가 이 이름들을 팀 멤버 spec에서 거부한다. 거부 사유가 결정적이다 — "process-mode 스폰(멤버에 필수)은 persona 지시와 도구 allowlist를 떨어뜨린다". 즉 읽기 전용으로 고정된 독립 검증자를 팀 멤버로 앉히는 경로가 현재 OMO에는 없다.

멤버별 permission을 spawn spec/argv로 전달할 경로가 없다

  • RpcRunnerSpec의 필드는 task_id, cwd, state_dir, prompt, resumeSessionPath, model, reasoning, variant, extensions, memberEnv뿐이다. permission 관련 필드가 없다.
  • buildChildArgs가 만드는 argv는 --no-extensions, --extension <path>(반복), --model, --thinking뿐이다. Senpi에 --permission-preset과 --permission이 실재하지만 OMO는 자식에 실어 보내지 않는다.
  • 설정 파일 우회는 기본값에서는 먹지 않는다. 비대화형 모드(-p, --mode json, --mode rpc)는 trust 프롬프트를 띄우지 않고 defaultProjectTrust(기본 ask)를 쓰며, ask와 never는 미신뢰 프로젝트 리소스를 무시한다. 그러나 해당 worktree의 trust 결정이 이미 저장됐다면 프로젝트 설정을 읽을 가능성이 있다.

따라서 gate 3은 pretrusted 전용 worktree 설정이 실제 RPC 멤버에서 역할별 정책으로 작동하는지 먼저 재는 문제다. OMO가 멤버마다 다른 worktreePath를 cwd로 넘기므로, 역할별 worktree를 따로 프로비저닝하면 디렉토리별 설정이 결과적으로 역할별 정책이 될 수 있다. 경계도 분명하다 — 같은 worktree를 두 역할이 공유하면 구분할 수 없고, verifier에는 read-only 프리셋의 "묻기"에 기대지 말고 edit·bash를 명시적으로 deny해야 한다(--mode rpc 자식에는 물음에 답할 사람이 없다). 또한 trust는 permission보다 넓은 문을 연다 — 프로젝트 리소스·패키지 설치·프로젝트 확장 실행까지 허용하므로 defaultProjectTrust: "always"를 전역에 켜는 형태는 기본 해법으로 삼지 않는다.

구조 변경으로 갈 때의 직접 접합점은 OMO child argv다. OMO는 open_session을 호출하지 않고 senpi --mode rpc 프로세스를 직접 띄운다. 가장 작은 upstream 변경 후보는 멤버별 permission 값을 RpcRunnerSpec에 넣고 Senpi의 기존 --permission-preset/--permission 플래그로 전달하는 배선이다.

그 밖에 어긋나는 둘

  • worktreePath는 git worktree를 만들지 않는다. mkdir -p로 평범한 디렉토리를 만들고 그 경로를 자식의 cwd로 넘길 뿐, git worktree add는 어디에도 없다. 실제 worktree 생성은 호출자가 미리 해 두어야 한다.
  • owner/verifier/budget/done-evidence 상태 모델이 부분적이다. 예산은 팀 런 수준으로는 있다(maxMembers 8, maxParallelMembers 4, maxMessagesPerRun 10000, maxWallClockMinutes 120, maxMemberTurns 500). 없는 것은 (a) 위임 단위의 예산과 반환 계약, (b) 완료 증거 필드, (c) owner와 verifier를 구분하는 역할 타입 — 멤버의 agentType은 leader 아니면 general-purpose 둘뿐이다.

필요한 것 — 어댑터로 되는 것과 gate

어댑터로 되는 것 둘.

  1. 승인 gate — 자식을 만드는 세 도구의 호출을 실행 전에 가로채 배치안을 사용자에게 보이고 승인 전에는 통과시키지 않는다. Senpi 확장이 도구 호출을 가로채거나 막을 수 있으므로 접합점이 있다.
  2. 완료 증거와 예산 반환 — Task 스키마의 metadata가 자유 레코드이므로 여기에 싣는다. 엔진이 강제하지 않으므로 강제는 우리 어댑터가 한다.

어댑터가 아닌 것. 나머지는 gate 1~6이며 다음 절에 모았다. 여기에 gate가 아닌 추가 작업 하나가 붙는다 — worktree provisioning: worktreePath를 채우기 전에 실제 git worktree add를 우리가 돌린다.

이 절은 확정 설계가 아니라 실패 가능한 가설이다. gate 1~6 중 하나라도 깨지면 후보 선택으로 되돌아간다.

  1. rubato-pi launcher (우리 것 — OMO launcher 대체)

    • -e <omo-ai>/plugin/extensions/omo.js ← 파일 단위. 디렉토리 아님.
    • -e <우리 어댑터 확장> ← 반드시 OMO 다음.
    • component disable 플래그 (gate 5 통과 시).
  2. Senpi engine ← 우리 어댑터 확장 승인 gate / 역할 라우팅 / verifier 권한 / 완료 증거 / worktree provisioning
  3. OMO 확장 (설치만, 포크 없음) task ON · 나머지 17개는 결정표에 따름 · OMO 스킬은 파일 단위 적재로 자동 배제(실측)

정확 pin을 쓰는 이유

omo-ai가 이미 엔진을 정확 버전으로 pin 하고 launcher가 self-update를 거부한다. 우리는 그 위에 omo-ai 자체도 고정한다. 근거는 이 레포가 아는 실패 모양이다 — 파일 diff가 깨끗하고 빌드가 통과하는데 의미만 틀어지는 조용한 실패. Senpi 릴리스 빈도가 높다는 점(npm에 122개 버전, 최근 5일에 6개)이 이 선택을 더 강하게 만든다.

확장 적재 형태 — 파일 단위 -e가 답이다 (실측)

앞선 초안은 settings packages에 객체 형태 필터로 설치해 스킬을 걸러 내자고 추천했다. 그 추천은 내렸다. settings로 적재된 확장은 process.argv에 없고, team-service.ts가 멤버 확장을 조립할 때 쓰는 inheritedExtensions: parseExtensionEntries(process.argv)는 부모 argv의 -e 항목만 긁는다. 그러면 멤버 자식은 --no-extensions만 받은 채 뜬다.

-e 순서가 의미를 갖는다

buildChildArgs에서 DAG가 소유한 자식은 상속 목록의 첫 항목을 slice(1)로 버린다. 주석이 이유를 밝힌다 — "The OMO launcher prepends its own extension before user/provider entries", 즉 첫 항목이 OMO 확장이라고 가정하고 DAG 자식이 또 다른 task 엔진을 부팅하지 못하게 막는 것이다. OMO 확장을 첫 -e로, 우리 어댑터를 그 뒤로 둔다. 순서를 뒤집으면 DAG 자식이 우리 어댑터를 잃고 OMO task 엔진은 유지하게 되어 의도와 정확히 반대가 된다.

자식 종류마다 목록이 다르게 조립된다는 점도 함께 봐야 한다.

  • 일반 task 자식 — 시작 spec에 extensions가 없으므로 process 러너가 inheritedExtensions(부모 argv의 -e)를 채운다. 멤버가 아니므로 task component가 등록되어 중첩 위임이 된다 — 막히는 것은 팀 멤버와 DAG 자식이지 모든 자식이 아니다.
  • DAG 자식 — 같은 목록을 받되 첫 항목이 버려진다.
  • 팀 멤버 — assembleMemberExtensions가 멤버 확장 번들을 첫 항목에 두고 그 뒤에 상속분을 붙인다. DAG 소유가 아니므로 slice(1)이 적용되지 않는다. 반대로 멤버가 아닌 자식에서는 buildChildProfile이 그 번들을 걸러 내고 멤버 식별 env도 지운다 — "같은 운반체, 다른 계약"의 구현체다.

소스만 보면 우리 어댑터는 세 갈래 모두에 실린다(DAG 자식에서는 OMO가 대신 빠진다). gate 1·2·6과 gate 3 PoC 실패 뒤의 해법으로 "자식에 강제 적재되는 우리 확장"을 검토할 수 있는 근거가 이것이고, 동시에 이것이 소스 독해일 뿐 실행 확인이 아니라는 것이 gate 4다.

gate 1~6

순서는 4 → 5 → 3 → 6 → 1 → 2가 자연스럽다. 확장 상속과 component 차단이 성립해야 나머지 해법 형태를 결정할 수 있기 때문이다. 스킬 차단은 더 이상 gate가 아니다 — 파일 단위 -e로 해결되는 것이 실측됐다.

gate 1 팀원의 중첩 위임 상태: 소스로 불가 확정

isTeamMemberProcess() early return을 지나갈 방법이 필요하다. upstream 변경, senpi-task+components/task fork, 또는 자식에 강제 적재되는 우리 확장이 위임 도구를 다시 제공하는 것 중 하나다.

깨지면: 후보 B로 승격 (포크 범위는 senpi-task + omo-senpi/components/task).

gate 2 역할 계약의 무조건 주입 상태: 소스로 경로 부재 확정

역할별 멤버 확장 또는 역할별 시스템 프롬프트 계층이 필요하다. member.prompt도, 계약 파일 경로 포인터도 보장 수단이 아니다.

깨지면: 후보 B로 승격.

gate 3 verifier 쓰기 차단 (멤버별 permission) 상태: 전용 worktree E2E 미측정

먼저 역할별 전용 worktree를 pretrust하고 프로젝트 설정에서 edit·bash를 명시적으로 deny한 뒤 RPC 멤버에서 E2E로 확인한다.

깨지면: child argv 배선(RpcRunnerSpec + Senpi 기존 플래그), fork, 또는 자식 강제 확장의 도구 호출 거부로 올라간다. worktree 공유가 필수인 경우도 같다.

gate 4 팀원 자식의 확장·disable 상태 상속 상태: 미측정 (리드 단독만 실측)

둘을 한 번에 만족해야 한다 — (a) 파일 단위 -e로 띄운 리드에서 팀원을 스폰했을 때 자식 argv에 같은 확장 경로가 실린다, (b) 부모의 component disable 상태가 자식에도 동일하게 적용된다.

(b)가 더 위험하다. parseExtensionEntries는 -e/--extension만 긁으므로 부모에서 memory를 껐어도 자식은 그것을 모른 채 뜰 수 있다.

깨지면: 후보 A 재검토 (task/team 재구현 비용과 재비교).

gate 5 component disable 플래그를 세울 수 있는가 상태: beta.7에서 실패, dev 미측정

플래그가 소스에 있다는 것과 우리가 세울 수 있다는 것은 다르다. dev pin에서 다시 재야 하고, dev에서도 안 되면 "필요한 것만 켠다"는 후보 C의 전제가 무너진다.

깨지면: 다른 경로(설정 파일, 환경변수)를 찾거나, 원치 않는 component가 켜진 채로 사는 비용을 받아들이거나, 후보 B로 올라간다.

gate 6 팀원의 board 직접 접근 상태: 소스로 현재 경로 부재 확정

member extension에 최소 task_list/task_get/task_update와 자기 이름 기반 claim 권한을 안전하게 추가해야 한다. 리드 중개 board는 비호환 축소안일 뿐 gate 통과로 간주하지 않는다.

깨지면: 제공할 수 없으면 후보 B로.

운영에 딸린 결정 셋

  • component allowlist와 update gate. allowlist는 코드가 아니라 launcher가 조립하는 플래그 목록으로 둔다. 버전을 올릴 때 component 목록의 diff를 먼저 본다 — upstream이 추가한 component는 기본적으로 켜져서 들어온다(compose.ts가 각 플래그 default를 "비활성화 안 함"으로 등록). 늘어난 이름은 결정표에 추가하고 결정 칸을 비운 채 사용자에게 올린다.
  • Taskforce role/member 어댑터. 어댑터로 되는 둘(승인 gate, 완료 증거·예산)은 우리 레포에 둔다. gate 1·2·6과 gate 3 PoC 실패 뒤의 구조 해법은 gate 4를 확인한 뒤에야 가장 작게 정할 수 있다.
  • 전용 brand/state/launcher. OMO launcher가 주입하는 것(SENPI_BRAND, SENPI_CODING_AGENT_DIR, OMO_NATIVE)을 우리 값으로 바꾼다. 상태 디렉토리 분리가 특히 중요하다 — 공유하면 두 제품이 같은 세션·인증 파일을 만진다.

team board 접근 (gate 6)팀원이 직접 list/get/update하고 자기 이름으로 claim하는 시나리오를 실행. 리드 중개는 호환 판정에서 제외팀원이 자기 상태를 갱신할 수 없거나, 권한 범위를 넘어 다른 owner의 task를 claim/update한다

팀원 모델 확인

fx 어댑터가 이미 요구하는 것이 여기서도 그대로 적용된다: 모델 id가 실제로 어디에 닿는지 실제 호출로 확인한 뒤에 그 역할을 맡긴다. 카탈로그에 이름이 보이는 것은 그 모델이 뜬다는 증거가 아니고, 독립 검증자가 조용히 owner와 같은 모델이면 검증이 아니다.

09라이선스와 배포 제약

두 저장소의 라이선스가 다르고, 이 차이가 후보 선택에 실제로 영향을 준다.

Senpi (code-yeongyu/senpi) — MIT. npm 패키지와 GitHub 저장소 메타데이터 양쪽에서 MIT. 재배포·상업 이용에 제약이 없다.

OMO (code-yeongyu/oh-my-openagent) 루트 — Sustainable Use License v1.0. 원문 Limitations의 범위는 이렇다.

  • 소프트웨어를 자신의 내부 업무 목적, 비상업적 목적, 개인 용도로만 사용하거나 수정할 수 있다.
  • 타인에게 배포하거나 제공하려면 무상이고 비상업적 목적이어야 한다.
  • 라이선스·저작권 고지를 변경·제거·은폐할 수 없다.
  • 제3자 구성요소는 각자의 원래 라이선스를 따른다.

OMO plugin 하위(plugin/LICENSE)는 MIT지만 범위가 좁다 — "Senpi LSP adapter descriptor, schema, renderer, path extraction, post-edit wiring, migration-warning helper 부분"에만 적용된다고 명시한다. plugin 디렉토리 전체가 MIT라는 뜻이 아니다.

실무적 귀결

  • 개인·내부 사용은 A/B/C 셋 다 문제없다. 지금 rubato-pi의 용도가 이것이라면 라이선스는 후보 선택을 좌우하지 않는다.
  • 외부 배포나 상업 제공을 하려면 OMO 코드를 포함한 B와 C가 막힌다. C에서 배포물이 "설치 지시와 우리 어댑터뿐"이면 OMO 코드가 없지만 — 이것은 법률 판단이며 이 문서가 결론 내릴 수 없다.
  • 후보 A만이 이 제약에서 완전히 자유롭다. 배포 계획이 전제로 깔리면 A의 상대적 가치가 올라간다.
  • 브랜드 교체는 라이선스 고지 제거와 다르다. SENPI_BRAND를 바꾸는 것은 설정 주입이지만, LICENSE·NOTICE 파일을 지우는 것은 명시적 금지 사항이다.

10열린 결정

component 18개의 선택은 결정표가 유일한 자리다. 여기서는 나머지를 모은다.

구조 결정

  • 후보 A / B / C 중 무엇으로 갈 것인가. 후보 C를 첫 PoC로 돌리는 데 동의하는지가 먼저 정해져야 한다.
  • rubato-pi가 기존 rubato(fx)를 대체하는가, 병행하는가, 특정 역할만 가져가는가.
  • 정확 pin의 갱신 주기와, 누가 component allowlist를 갱신하는가.
  • 외부·상업 배포 계획이 있는가. 있다면 후보 선택이 라이선스 제약을 받는다.

PoC gate — 순서와 판정자

  • gate 4 — 팀원 자식이 (a) 같은 확장 경로를 상속받는가, (b) 부모의 disable 상태도 물려받는가.
  • gate 5 — dev pin에서 --omo-senpi-<name>-disabled가 실제로 component를 끄는가. 안 되면 어떤 경로로 세울 것인가.
  • gate 3 — pretrusted 역할별 전용 worktree의 명시적 edit·bash deny가 RPC 멤버에서 작동하는가. 실패하면 child argv 배선 / fork / 자식 강제 확장 중 어디로 올라갈 것인가.
  • gate 6 — member extension에 board 도구와 자기 이름 기반 claim을 어떤 권한으로 제공할 것인가.
  • gate 1 — early return을 어떤 방법으로 지나갈 것인가. upstream 변경 / fork / 자식 강제 확장 중 무엇인가.
  • gate 2 — 역할 계약 주입 계층을 역할별 멤버 확장으로 만들 것인가, 역할별 시스템 프롬프트로 만들 것인가.
  • 승격 판정 — 승격 기준 둘 중 하나에 걸리면 후보 C를 접고 B로 올린다. 누가 그 판정을 내리는가.

측정해야 결정할 수 있는 것

  • task component ON의 프롬프트 토큰 비용(도구 11개 + 에이전트 설명)이 얼마인가.
  • 결정표에서 "보류"로 남긴 component 각각이 어떤 지표를 봐야 결정되는가.

로컬 실측 절차 (2026-08-22)

  1. Senpi CLI를 --mode rpc --no-context-files --no-prompt-templates로 띄우고 적재 형태별로 -e 인자만 바꾼다.
  2. 부수효과 격리: SENPI_CODING_AGENT_DIR를 빈 임시 디렉토리로, PI_OFFLINE=1, DO_NOT_TRACK=1, OMO_DISABLE_POSTHOG=1, cwd도 빈 임시 디렉토리. 실제 ~/.omo나 ~/.senpi는 건드리지 않는다.
  3. stdin으로 {"type":"get_commands"}를 보내고 commands 배열을 source별로 센다. source: "skill" 행이 적재된 스킬이다. 모델 호출이 없으므로 비용이 들지 않는다.
  4. disable 플래그는 같은 절차에 인자를 추가하고 표면 차이를 본다. 알 수 없는 플래그는 CLI가 Unknown option으로 거부하므로, 거부되지 않았는데 표면이 그대로면 "인식은 되지만 반영되지 않는" 상태다 — beta.7이 이 상태였다.
